\section{Results Achieved}

This project achieved its core goal: understanding, first-hand, how a modern streaming platform works end to end. Building the pipeline meant learning why a Kafka partition needs a follower replica, why Structured Streaming's checkpoint must be separate from the consumer-group offset it also commits, when MERGE\_ON\_READ is worth its read-time merge cost over COPY\_ON\_WRITE, and how a fixed, shared compute budget shapes every downstream decision.

It also applied the course's distributed-systems concepts -- partitioning and replication, checkpointed exactly-once processing, and consumer-lag observability -- to a real system. In practice, the streaming lakehouse closes the gaps from Section~\ref{sec:problem-before-lakehouses}: no duplicated lambda speed layer, a transactionally updatable lake, and independent storage and compute. The whole stack comes up reproducibly from one Docker Compose command.

\section{Limitations}

\begin{itemize}
    \item \textbf{Small, fixed-size cluster.} The Spark cluster has only 4 cores, shared by the streaming job and the Thrift Server used by dbt, so there is no headroom for ad-hoc Spark SQL.
    \item \textbf{No autoscaling.} Kafka brokers and Spark workers are fixed at deployment time.
    \item \textbf{Synthetic dataset.} Eventsim data has not been validated against real traffic patterns or data-quality issues.
\end{itemize}

\section{Future Directions}

\begin{itemize}
    \item Validate the pipeline with a real or real-scale streaming dataset.
    \item Add autoscaling for Kafka and Spark (e.g. via a container orchestrator).
    \item Add automated alerts (consumer lag, job failures) and a silver layer between bronze and gold.
\end{itemize}
